Сессия ≠ процесс

OpenCode различает четыре вещи, и они путаются между собой. Первый урок — научиться их не путать.

Вопрос, из которого вырос этот урок

Есть четыре идентификатора. Три из них выглядят как «имя процесса», но ведут себя по-разному. Вопрос: какой из них переживёт перезапуск сервиса, а какой нет?

ИдентификаторГде лежитПохоже на имя процесса?
session_idБД, ses_+26 симв.да
instance UUIDservice.jsonда
pid из /api/infoотдаёт сервисда
run в логетолько grep по логуда

Интуиция говорит: instance UUID — это «имя установки», он обязан переживать рестарт. Это неверно. На этой машине проверено четырьмя перезапусками изолированного инстанса:

старт 1: fff38e17-4648-40b2-bf31-c1dd719f38ac  pid 32333
старт 2: 38383ff6-06bc-4570-b344-992fb7e28e3e  pid 32381
старт 3: 129b8582-d3dd-4929-8d01-d9f768c9fb1c  pid 32406
старт 4: ab7c0b00-ab0c-49c8-a55e-ebd831cd2ea7  pid 32504

Один и тот же каталог состояния, тот же порт, четыре разных UUID. Он генерируется заново при каждом старте.

Что переживает рестарт

Сессия создаётся в БД, и БД перезапуск не трогает. Проверено: сессия ses_ef2f72252ffe25fcYS2o9XeAcS создана через POST /api/session, затем процесс убит и поднят заново — сессия читается и после.

Пароль сервиса тоже пережил рестарт, в отличие от UUID. Это не документировано нигде.

Почему это важно для поиска. Если искать «что делал агент вчера», сессия — единственное, что выживёт. UUID сменился, run исчез, pid новый. Остаётся ses_….

Про pid — отдельная ловушка

/api/info отдаёт pid. Выглядит как pid процесса. На деле это pid фонового сервиса, а он общий для всех агентов на машине:

$ opencode api get /api/info
{"version":"2.0.22","pid":12279, ...}

Пять агентов на этой машине, у всех в логе один и тот же pid 12279. Включать его в ключ идентичности бессмысленно — он не различает ничего.

Про run — единственный, кто различает процессы

run=<8 hex> стоит в каждой строке лога. Это единственное поле, которое уникально для процесса в момент его жизни. Но:

  • в окружении его нет — только OPENCODE_SESSION_ID, OPENCODE, OPENCODE_TERMINAL
  • в API его нет — /api/session/{id}/log отдаёт сообщения сессии, не run
  • в логе он есть у 118762 строк из 118762, так что в этом смысле он полон
  • связь run↔session — many-to-many: 54 run встречаются с несколькими сессиями, 19 сессий — с несколькими run

Достать его можно только grep'ом, и он может вернуть не один результат.

Что дано штатно

$OPENCODE_SESSION_ID — переменная окружения, которую opencode экспортирует в каждый процесс. Это и есть ответ на исходный вопрос «как найти сессию»: не нужен ни API, ни лог, ни БД.

$ echo $OPENCODE_SESSION_ID
ses_ef3bd28b8ffedrxhMBdkA9Xem4

Проверь себя

Какой идентификатор переживает перезапуск сервиса opencode?

Ни один из четырёх. session_id — единственный, кто переживает рестарт. UUID генерируется заново при каждом старте, pid меняется, run не переживает рестарт и достаётся только из лога.

Откуда берётся значение run при поиске сессии?

Только из лога. В окружении его нет, в API нет, в БД нет — он генерируется как randomUUID().slice(0,8) и пишется в строки лога.

Сделай сам

Три команды, каждая должна дать осмысленный вывод:

# 1. твоя сессия — из окружения, без API
echo $OPENCODE_SESSION_ID

# 2. метаданные сессии: агент, проект, родитель
opencode api get /api/session/$OPENCODE_SESSION_ID

# 3. run твоей сессии — только так
grep "$OPENCODE_SESSION_ID" ~/.local/share/opencode/log/opencode.log \
  | grep -oE 'run=[0-9a-f]{8}' | sort -u

В третьей команде посчитай, сколько разных run вышло. Если больше одного — это тот many-to-many из §«Про run», и это нормально.

Источник для чтения

Первоисточник, который стоит прочитать целиком: OpenCode V2 — Troubleshooting. Это единственная страница документации, где упомянуты run, role, путь к логу и файлы service.json. Обрати внимание на разделение ~/.local/state/opencode/service.json (регистрация сервера) и ~/.config/opencode/service.json (пароль) — два разных файла, при переносе конфигурации нужны оба.
